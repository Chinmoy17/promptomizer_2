\title{Beyond Aggregate Accuracy: Item-Level Transitions in Prompt Optimization}

% ARR review submissions must be fully anonymous.

\begin{abstract}
Language-model systems are often configured through natural-language instructions, or prompts, that specify tasks,
relevant context, and response requirements. Automatic prompt optimization revises these instructions using feedback
from model outputs, but an aggregate before/after score does not identify which evaluated cases improve or deteriorate.
We present RFDPO, an auditable measurement framework that preserves prompt revisions, records item-level recoveries,
regressions, and churn, and accounts for token consumption and API costs. We use its records to examine prompt revisions
across five benchmark families and two solver models. Small net score changes can coexist with substantial movement
between correct and incorrect outcomes. Validation improvements often accompany test improvements, but their magnitude
and direction need not agree. These observations motivate evaluating prompt optimization as a sequence of measured
behavioral changes, not only a final score. We recommend reporting paired outcome transitions alongside tuning and test
performance, fixed-configuration evaluation controls, and resource use. This account supports inspection of what
revisions improve, disrupt, and preserve, without attributing every observed transition to the revision itself.
\end{abstract}

\section{Introduction}
\label{sec:intro}

Language models are used to classify documents, extract information, answer questions, and follow instructions.
These systems can be configured with a \emph{prompt}: natural-language instructions supplied alongside the task input
to describe the task, relevant context, constraints, and response format. For example, an extraction prompt can specify
which fields to return and how to represent missing values. Small changes in wording or formatting can substantially
affect performance without changing model parameters~\citep{sclar2024quantifying}.

Manual prompt refinement alternates between editing instructions and evaluating outputs.
\emph{Automatic prompt optimization} (APO) automates this search~\citep{zhou2023ape,yang2024opro,pryzant2023protegi}.
In LLM-based approaches, a \emph{solver} performs the task while an \emph{optimizer} receives the current prompt and
evaluation feedback and proposes a revision. Candidate outputs or scores inform subsequent rewrites; solver parameters
remain fixed. These are distinct roles, not necessarily different model architectures. Here, GPT-5 rewrites prompts
for GPT-4o-mini and GPT-4.1 Mini solvers.

For an engineer refining document extraction or retrieval-augmented question answering, where retrieved documents
accompany a query~\citep{lewis2020rag}, the consequences of each edit matter: which failing cases now work, which correct
cases break, and which failures remain. \textbf{These observations can inform the next edit.} Many APO methods already
inspect failures or execution traces, but aggregate before/after reporting hides these transitions.

A net gain of two items, for example, can mean two corrections with no regressions or ten corrections offset by eight
regressions. The scores agree, but the changes warrant different inspection. On the small evaluation sets often used
in prompt optimization, near-flat accuracy can conceal substantial movement between correct and incorrect outcomes
(\S\ref{sec:results}).

An additional question is \textbf{whether gains generalize}. Candidates are often compared on a \emph{validation set},
whose examples may also provide optimizer feedback. Improvement on these tuning examples need not transfer to unseen
data. Repeated selection can produce optimistic validation scores; evaluation noise and dataset shift can also explain
validation/test differences~\citep{recht2019imagenet}.

We track \emph{recoveries} (incorrect to correct), \emph{regressions} (correct to incorrect), and \emph{churn} (all
changed outcomes). These are measurements of paired evaluations, not new optimization objectives. We implement them
in \emph{Reflective Feedback-Driven Prompt Optimization} (RFDPO), a framework that versions prompt revisions, records
outcome transitions, and meters token consumption and API costs (Figure~\ref{fig:arch}). Its optimization loop returns
transition observations to an LLM rewriter; here, that loop is the instrument used to collect evaluation records,
not a treatment whose advantage over other feedback strategies is established.

We analyse recorded runs on LegalBench-Hearsay, MMLU, IFBench, AIME, and PUPA with GPT-4o-mini and GPT-4.1 Mini solvers.
Our question is what paired outcomes reveal beyond the aggregate score, including how tuning-time gains compare with
test changes. Within a run, test examples are excluded from optimizer feedback and candidate selection. Our contributions are:

\begin{itemize}\setlength{\itemsep}{2pt}\setlength{\parskip}{0pt}\setlength{\topsep}{2pt}
\item \textbf{An auditable measurement framework.} RFDPO integrates prompt-version history, paired correctness transitions,
and per-role token and cost accounting (\S\ref{sec:method}).
\item \textbf{A descriptive empirical analysis.} Recorded evaluations expose recovery/regression trade-offs behind small
net changes and differences between tuning and test gains (\S\ref{sec:results}).
\item \textbf{Actionable reporting guidance.} We identify the outcome records, controls, and resource measurements needed
to inspect prompt revisions beyond aggregate accuracy (\S\ref{sec:discussion}).
\end{itemize}

Together, these observations motivate treating recovery, regression, churn, and validation-to-test transfer as
\textbf{first-class reporting dimensions for APO}, alongside aggregate accuracy.

\section{Related Work}
\label{sec:related}

\paragraph{Prompt optimization.}
APO has progressed from discrete token-level search~\citep{shin2020autoprompt}
and generate-and-score instruction search~\citep{zhou2023ape}, to LLMs used as
optimizers over trajectories of scored prompts~\citep{yang2024opro}, textual-gradient
edits~\citep{pryzant2023protegi,yuksekgonul2025textgrad}, evolutionary
search~\citep{guo2024evoprompt,fernando2024promptbreeder}, and multi-stage pipelines
optimized jointly over instructions and demonstrations~\citep{opsahlong2024miprov2,schnabel2024sammo}, many of them packaged in
programming frameworks such as DSPy~\citep{khattab2024dspy}.
Closest to our prompt schema is MPO~\citep{sharma2026mpo}, which decomposes a prompt
into the same five semantic sections and applies section-local textual gradients;
its updates are additive and de-duplicated. Our analysis makes observed correct-to-incorrect transitions explicit without
using them as an acceptance gate. GEPA~\citep{agrawal2026gepa} combines reflective
prompt mutation with Pareto-based selection over a population of prompts, and
Trace2Policy~\citep{zha2026trace2policy} refines a rule document by clustering errors and committing
patches that pass a regression gate. General self-feedback methods return verbal critiques to the
model that produced an output~\citep{madaan2023selfrefine,shinn2023reflexion}. Reflection and regression testing are therefore
not new here. Our focus is explicit before/after transition accounting in feedback and reporting, not priority over
trace-based reflection or a demonstrated advantage over these methods.

\paragraph{Published results use different protocols.}
Table~\ref{tab:prior} lists how prior work set up the benchmarks we share, next to our own setup. No two rows are measured the same way.
Benchmarks are re-split: the official LegalBench-Hearsay split is 5 training and 94 test items, and every paper recuts it. Test sets
range from 30 to 1,400 items. Solvers range from 7B open-weight models to frontier APIs. Baselines differ in what they already
contain: the AIME baseline in GEPA is a DSPy chain-of-thought module that forces a reasoning field into every generation, whereas
ours is a bare five-section seed. Refinements are written by an LLM in most rows and by a human curator in one, and the number of
repeated evaluations differs. A before/after change from one row therefore says little about what the same method would do under
another row's protocol, and on test sets of 30 to 66 items a single run's change is mostly within evaluation noise
(Appendix~\ref{app:noise}).

\paragraph{State-of-the-art accuracy is not our goal.}
We do not try to beat these numbers and we do not rank methods by them. Our questions are what a prompt edit does at the item level
and how much of an optimization-time gain survives on unseen data. Both can be asked of any optimizer at any accuracy level, and
the answers do not depend on the absolute scores in Table~\ref{tab:prior}. We therefore cite prior systems for their mechanisms and
include our own rows only to make the differences in protocol visible.

\paragraph{Evaluation beyond accuracy.}
Our framing, that one aggregate number hides qualitatively different behaviors, follows
CheckList~\citep{ribeiro2020checklist}, which showed that models passing standard
benchmarks fail systematically on targeted tests. CheckList evaluates a fixed trained
model; we instead track per-item outcomes across the successive edits of an optimization
process. A validation/test gap is consistent with adaptive tuning, but it does not identify adaptive overfitting separately
from sampling noise or dataset shift~\citep{recht2019imagenet}. Test-set memorization is another concern, which
\citet{oren2023proving} show can be detected in black-box language models; we check for
verbatim copying directly (\S\ref{sec:valtest}).

\paragraph{Test-set exposure.}
Trace2Policy's own appendix reports that one refinement round for its headline LegalBench-Hearsay
result was diagnosed partly from the nominally held-out test set~\citep{zha2026trace2policy}.
To measure how sensitive this task is to such exposure, we ran an earlier, simpler variant of our optimizer
with the sealed test pool deliberately used as the mining set (Claude Haiku 4.5 \citep{anthropic2025haiku45} as solver, outside the main
experiments). It moved accuracy from 68.8\% to 95.3\%. This diagnostic is invalid as a result and we report it
only as a caution: a test-exposed trajectory can produce a much larger reported gain. This single diagnostic does not
isolate exposure from trajectory or evaluation noise, and does not establish anything about another method's results.

\section{Measurement Framework}
\label{sec:method}

\subsection{Setting}
In this study, we represent each prompt using five fixed sections: System Role, Context, Task Details, Constraints,
and Output Format, following the structured-prompt formulation of MPO~\citep{sharma2026mpo}. This representation is an
experimental design choice, not a general requirement for prompts. The seed prompts use the same schema and specify
the task, required answer format, and applicable definitions or constraints. We retain the section headers throughout
optimization and record which sections each revision changes. A shared schema makes section edits comparable, but
does not eliminate dependence on the seed prompt's content. A solver LLM performs the task under each prompt;
an optimizer LLM rewrites the instructions without updating the solver's parameters. In our experiments, the solver
model is distinct from the optimizer and any LLM judge.

Each benchmark's data is split into three disjoint pools: a \emph{mining} set $M$ whose outcomes provide optimizer
feedback, a \emph{validation} set $V$ used for candidate selection and, from round 2, whose changed outcomes also
provide feedback, and a \emph{test} set $T$. Thus $M$ and $V$ are tuning sets, not independent evidence of
generalization. Within a run, test examples are excluded from optimizer feedback and candidate selection and are
evaluated only with the seed and returned prompt for baseline and final reporting. This run-level protocol is
distinct from development-time use of test traces, discussed in Limitations.

\subsection{Recovery/regression tracking}
\label{sec:metric}
Let $c_i(p)\in\{0,1\}$ denote the observed scored outcome in one evaluation under prompt $p$ (for
PUPA, whether the composite score passes a fixed threshold of 0.7). Take a prompt $p$ and an edited prompt $q$ scored on the same
item set $D$ (Figure~\ref{fig:metric}). An item is \emph{recovered} if it was wrong under $p$ and right under $q$, and
\emph{regressed} if it was right under $p$ and wrong under $q$. We write $R$ and $G$ for the two sets, so
$R=\{i\in D: c_i(p)=0,\ c_i(q)=1\}$ and $G=\{i\in D: c_i(p)=1,\ c_i(q)=0\}$. Two numbers summarize them:
the \emph{net change} $N=|R|-|G|$, which equals $|D|$ times the accuracy change, and the \emph{churn} $C=|R|+|G|$, the number of
items that flipped in either direction. Two edits with the same $N$ cannot be told apart by accuracy even when their churn differs greatly.

\begin{figure}[!t]
\centering
\includegraphics[width=\columnwidth]{figures/fig_metric.pdf}
\caption{Worked example on ten items. Three items go from wrong to right (recovered, green) and two from right to wrong
(regressed, red), so accuracy rises by one item (net $+1$) while five items changed (churn $5$).}
\label{fig:metric}
\end{figure}

We compute $(R,G)$ between consecutive rounds on $M$ and $V$, and between seed and returned prompts on $T$, using the same
evaluable item IDs in each pair. PUPA's $N/|D|$ equals its thresholded accuracy change, not its composite-score change.
MMLU counts are summed over subjects while accuracy is macro-averaged. API variability means these are observed
transitions, not proof that an edit caused a recovery or regression. AIME transition counts follow the supplied summary
and the author's confirmation rather than matched archived logs.

\subsection{RFDPO Recording Procedure}
Algorithm~\ref{alg:reflect} gives the procedure and Figure~\ref{fig:arch} its data flow. Round
$t=1$ has nothing to reflect on. From round 2 the optimizer is shown, in full and without sampling, the items its
previous rewrite recovered and regressed on both $M$ and $V$ (the question, the solver's new wrong answer, and the gold
answer), the previous text of every section it changed, and the validation accuracy before and after.
Each valid, changed candidate is saved (\emph{committed}) and becomes the starting prompt for the next round, even
when validation accuracy decreases. Under the current selection rule, we return the committed candidate with highest
validation accuracy (Appendix~\ref{app:prompts}). When two candidates obtain the same validation accuracy, we select
the candidate with higher mining accuracy. If both accuracies are equal, the earlier candidate remains selected.
The seed is not included in this comparison once a candidate has been committed, so the returned prompt need not
improve validation accuracy relative to the seed. If no candidate is committed, the seed is retained.
Some archived runs instead used final-round selection; Appendix~\ref{app:gap} distinguishes the selection rules.
Optimization is skipped when the seed scores at least 95\% on $M$ (except PUPA),
and a round that proposes no change is skipped. The optimizer is instructed not to copy
dataset items into the prompt (\S\ref{app:history}). Appendix~\ref{app:design} gives, for each design decision, the
alternative we rejected and the values from our saved runs that support the choice.

\begin{algorithm}[!t]
\caption{RFDPO recording and candidate selection}
\label{alg:reflect}
\small
\begin{algorithmic}[1]
\Require seed $p_0$; disjoint $M,V,T$; $\textsc{Opt}$; $\textsc{Solve}$; round budget $B$
\State $s_0,v_0 \gets \textsc{Solve}(p_0,M),\ \textsc{Solve}(p_0,V)$
\State $\tau_0 \gets \textsc{Solve}(p_0,T)$ \Comment{baseline; measured only}
\State $\mathcal{H}\gets\emptyset$; $(p,s,v)\gets(p_0,s_0,v_0)$; $\rho\gets\emptyset$
\For{$t=1$ \textbf{to} $B$}
  \If{skip threshold reached, or no mining failures} \State \textbf{break} \EndIf
  \State $q\gets\textsc{Opt}(p,s,v,\rho)$ \Comment{mining items and feedback}
  \If{$q=p$} \State \textbf{continue} \EndIf
  \State $s',v'\gets\textsc{Solve}(q,M),\ \textsc{Solve}(q,V)$
  \State $\rho\gets((R,G)(s\!\to\!s'),(R,G)(v\!\to\!v'))$
  \State append $(q,s',v')$ to $\mathcal{H}$ \Comment{no regression gate}
  \State $(p,s,v)\gets(q,s',v')$
\EndFor
\State $p^*\gets p_0$ if $\mathcal{H}=\emptyset$; otherwise select from $\mathcal{H}$
\Statex \hspace{\algorithmicindent} by validation accuracy, then mining accuracy
\State $\tau^* \gets \textsc{Solve}(p^*,T)$ \Comment{measured only}
\State \Return $p^*$, and $(R,G)(\tau_0\!\to\!\tau^*;T)$
\end{algorithmic}
\end{algorithm}

\section{Experimental Setup}
\label{sec:setup}

We use five benchmarks chosen to differ in task type, answer format, and metric (Table~\ref{tab:setup}); scoring is programmatic
except for PUPA's response quality (Appendix~\ref{app:eval}).

\paragraph{Benchmarks.}
\textbf{LegalBench-Hearsay} \citep{guha2023legalbench} asks whether a described statement is hearsay under U.S. evidence law, a binary
label that turns on a precise legal definition. \textbf{MMLU} \citep{hendrycks2021mmlu} is four-way multiple choice; we use six subjects
(college mathematics, computer security, econometrics, high school biology, philosophy, professional law) spanning calculation,
recall, and argument, and optimize each subject separately. \textbf{IFBench} \citep{pyatkin2025ifbench} contains prompts with
verifiable output constraints (for example, forbidden punctuation or a required keyword); an item counts as correct only if every
constraint is met, checked by code. IFEval \citep{zhou2023ifeval} shares this format and part of our verifier, but we report only
IFBench; an early IFEval pilot is not in the results. \textbf{AIME} problems \citep{maa2025aime} have integer answers from 0 to 999 and
require long reasoning; we mine on 2022 to 2024 problems and test on the 30 problems of the 2025 contests. \textbf{PUPA}
\citep{li2025papillon} is privacy-conscious delegation: the optimized prompt must rewrite a user query containing personal information
into a request that a stronger external model can answer without seeing that information, and the final response is scored on
quality and leakage (composite in Table~\ref{tab:setup}). Only the redaction step is optimized, so PUPA is the one multi-stage task.

\paragraph{Models.}
Solvers are GPT-4o-mini \citep{openai2024gpt4o} and GPT-4.1 Mini \citep{openai2025gpt41} (temperature 0). The optimizer is GPT-5 \citep{openai2025gpt5} (temperature 0.7). PUPA
additionally uses GPT-5 as its quality judge and a fixed, never-optimized GPT-4.1 \citep{openai2025gpt41} as the untrusted external model
in its rewrite--external-answer--synthesis pipeline. The solver is never the optimizer or the judge, and the PUPA external model differs from the solver.
Scoring details are in Appendix~\ref{app:eval} and the optimizer's instructions in Appendix~\ref{app:prompts}.

\paragraph{Protocol.}
We report one selected result per (benchmark, solver) pair, using seed 0 and at most three rounds; pilot runs and rechecks
exist and are not independent replications of this summary. MMLU subjects are optimized independently, giving 12 subject
records and 20 records overall. Eighteen non-AIME records support the matched transfer analysis. Splits, token budgets,
checker versions, and shipping rules differ in some solver pairs (Appendix~\ref{app:config}); this is not a controlled
cross-model comparison. Logged GPT-4.1 Mini run costs range from \$0.01 to \$4.80, excluding development and rechecks.

\paragraph{Limited copying check.}
We checked final prompts in the archived run collection (the seed when no edited prompt was returned) for shared 8-word sequences with
dataset items. Of the 18 non-AIME prompts corresponding to matched results, 15 share none. The remaining three share one
generic mathematical phrase (MMLU college mathematics, GPT-4o-mini) and a boilerplate pattern of True/False answer
options (MMLU computer security, both solvers). This offers no affirmative evidence of item copying, but cannot exclude
shorter copying, paraphrases, semantic memorization, or pretraining contamination. An anti-copying instruction is not a
verification of compliance (Appendix~\ref{app:overlap}).

\section{Discussion}
\label{sec:discussion}
\paragraph{What we recommend reporting.}
For any prompt optimizer: (i) report recovered, regressed, and churn counts on a common evaluable item set;
(ii) show tuning and test changes in the same metric; (iii) repeat the unchanged prompt under a fixed harness to estimate
evaluation variability; and (iv) publish run IDs, prompt hashes, configuration versions, denominators, and exclusions.
Transition accounting is cheap given per-item logs; repeated controls require additional inference.

\paragraph{What we do not show.}
Our results do not isolate whether showing the optimizer its own recovered/regressed record improves optimization:
we ran no matched ablation against failure-only feedback. The recovery/regression accounting is the contribution we
can support; Reflective FDPO is the instrument that produced the evidence. A matched comparison must hold the seed,
solver, item IDs, harness, candidate budget, and selection rule fixed, varying only transition feedback. No such experiment
is reported, and summary-only AIME gains do not fill that gap.

\section{Conclusion}
Per-item recovery/regression tracking turns an aggregate accuracy delta into a record of what an optimization actually
changed in a scored evaluation. Matched non-AIME records show large churn behind small net changes and three cases where
validation improved while test accuracy declined. Supplied AIME gains remain provenance-limited. The evidence supports
more informative reporting, not a claim of superior optimization: report transition counts, fixed-harness controls,
matched tuning/test metrics, and auditable provenance together.

\section*{Limitations}
\label{sec:limitations}
\paragraph{Scale and noise.} Each (benchmark, solver) pair has one seed and a test set of 30 to 66 items, so one item is worth
1.5 to 3.3 accuracy points. We report no confidence intervals or significance claims. Archived AIME rechecks changed
harness settings and therefore do not isolate API noise; observed transitions may include stochastic variation.
\paragraph{Not a state-of-the-art comparison.} We do not compare numerically against published systems, whose splits, solvers, and
baselines differ (Table~\ref{tab:prior}), and we make no state-of-the-art claim. We also ran no ablation isolating the reflection signal.
\paragraph{Fix-state asymmetry.} GPT-4.1 Mini runs on PUPA, IFBench, and AIME were measured after harness fixes that
GPT-4o-mini runs predate. Archived GPT-4o-mini runs on AIME, PUPA, IFBench, and six MMLU subjects used the historical
final-round rule. Even within-solver effects require fixed-harness repeats; cross-solver effects are not identified.
\paragraph{Development used test-time traces.} The harness decisions described in Appendix~\ref{app:noisebugs} (the AIME token cap, the PUPA judge limit, the IFBench checker) were made after inspecting traces that included
test items. These changed how outputs are generated or scored, not which items the optimizer could see, but $T$ was not entirely
outside the development loop for the harness.
\paragraph{Mechanism.} A returned edited prompt need not beat the seed on validation (two of 16 eligible edited-prompt
returns did not). The optimizer sees flipped validation items and, under the current rule, validation accuracy determines
the returned candidate, so $V$ is not held out and the
validation gains in Table~\ref{tab:gap} are optimistic by construction. Our IFBench verifier implements
a subset (32 of 83) of the constraint types in IFEval and IFBench combined, and PUPA scores depend on an LLM judge.
\paragraph{Models.} Only two closed-weight solvers and one optimizer/judge (GPT-5) were used, and API behavior can drift. We did not evaluate open-weight solvers.

\section*{Ethical Considerations}
Data come from public benchmarks, with resplitting and an AIME gold-label correction disclosed above. PUPA contains
personal information in public user--LLM conversations. Hosted solver and optimizer APIs may receive the original query
during evaluation and feedback; redaction protects only the designated external model, not the entire pipeline.
String-matched leakage misses paraphrased or inferred information and is not a privacy guarantee. The intended public
traces contain item IDs and outcomes only; raw inputs, predictions, gold text, and model-call bodies must be omitted or
sanitized before release (Appendix~\ref{app:artifacts}). Logged API fees do not establish environmental impact, which
we did not measure.

\subsection{Reporting churn}
\label{app:d1}
\paragraph{Proposition 1.} For prompts $p,q$ and an item set $D$, let $N=|R|-|G|$ and $C=|R|+|G|$ as in
\S\ref{sec:metric}. Then $\mathrm{acc}_D(q)-\mathrm{acc}_D(p)=N/|D|$, $C=|N|+2\min(|R|,|G|)$, and $|N|\le C\le |D|$ with
$C\equiv N \pmod 2$. Every such pair $(N,C)$ is attained by some pattern of outcomes.

\emph{Proof.} $R$ and $G$ are disjoint subsets of $D$, so $|R|+|G|\le|D|$. Items with $c_i(p)=c_i(q)$ contribute equally to both
accuracies, so the accuracy difference is $(|R|-|G|)/|D|$. Writing $C-|N|=(|R|+|G|)-||R|-|G||=2\min(|R|,|G|)$ gives the identity. For
any integers $R,G\ge 0$ with $R+G\le |D|$ an outcome pattern with $|R|=R$ and $|G|=G$ exists, and $R=(C+N)/2$, $G=(C-N)/2$ are
non-negative integers exactly when $C\ge|N|$ and $C\equiv N \pmod 2$. \hfill$\square$

\finding The net change constrains churn only from below. For Hearsay with GPT-4o-mini, $N=-1$ over $|D|=49$ permits
any odd $C$ from 1 to 49; the observed value is 17 (8 recovered, 9 regressed). Reporting $N$ alone would not distinguish this run from
one that changed a single item.

\subsection{Committing every round}
\label{app:d2}
Two retired designs used a regression gate (Appendix~\ref{app:history}): one rejected over 40\% of proposed edits with no improvement
trend, and one rejected net-positive trades outright. Four of the 17 matched non-MMLU committed rounds in Table~\ref{tab:rounds} lowered
validation accuracy relative to the previous round. The clearest case is Hearsay with GPT-4o-mini, where round 1 lowered validation
accuracy from 68.0 to 44.0 (seven items regressed) and rounds 2 and 3 reached 72.0 and 80.0, the run's best. A gate that rejected
round 1 would have discarded the lineage that produced the shipped prompt, although we cannot say what the later rounds would have
produced from the seed.
\finding Unconditional commits keep every lineage reachable. The cost is that the shipped prompt can score below the seed on
validation: two of the 16 eligible non-AIME shipped runs did.

\subsection{Selection rule}
\label{app:d3}
The shipped round is the committed round with the highest validation accuracy, ties broken by mining accuracy. Among the 11 runs with a
unique best-validation round, that round was round 1 in 2 runs, round 2 in 6, and round 3 in 3, so the last round was the unique best in
only 3. Nine early GPT-4o-mini runs shipped the last round instead (\S\ref{sec:method}); in 4 of them the shipped round scored below an
earlier round on validation, by 3.1 (AIME), 10.0 (PUPA), 15.8 (IFBench), and 4.5 (MMLU professional law) points, and in the other five
the last round was best or tied. Under the best-of-rounds rule the shipped round beat the last round on validation by 9.4 (AIME,
GPT-4.1 Mini), 12.0 (Hearsay, GPT-4.1 Mini), 4.0 (MMLU philosophy, GPT-4.1 Mini), and 13.6 (MMLU professional law, GPT-4.1 Mini)
points, and tied in the other five. Validation accuracy tied between rounds in 7 of the 18 runs that optimized, which is common when $V$
has 14 to 32 items, so the tie-break matters: in IFBench with GPT-4.1 Mini, rounds 1 and 3 tied at 71.4 and round 1 shipped on mining accuracy
(52.0 against 40.0).
\finding Validation accuracy is the selection criterion, so these gaps are non-negative by construction and are not evidence
of better test performance; the test comparison by rule in Table~\ref{tab:gap} is confounded by model and benchmark mix.

\subsection{Whole-prompt rewrite in a fixed schema}
\label{app:d4}
The optimizer returns the full markdown prompt, which the parser reads section by section. This replaced exact-substring edits, which
failed in repeated runs (Appendix~\ref{app:history}). Across all 53 optimizer calls in the 20 runs, none failed to parse and none omitted a
section; one call proposed no change and the round was skipped. Committed rounds edited a mean of 4.1 of the 5 sections in round 1
($n=18$) and 1.3 in rounds 2 and 3 ($n=34$; 23 of 34 edited a single section). Over all 52 committed rounds, Task Details was edited 50
times, Context 25, Constraints 21, System Role 12, and Output Format 11.
\finding The schema is well formed in every call, and edits concentrate in Task Details. The narrowing after round 1 is
confounded with later rounds having fewer failures left to address, so we do not attribute it to the effect report.

\subsection{Showing every item}
\label{app:d5}
The optimizer sees every failure and every success on $M$, and every flipped item on $V$, with no sampling, so it knows what must not break.
This is affordable at our scale. Mean optimizer input per call was 5.2K tokens (4.7K to 5.7K) for Hearsay, 7.3K (6.7K to 7.8K) for
IFBench, 6.8K (4.6K to 10.9K) for MMLU, 23.7K (22.8K to 24.6K) for PUPA, and 180K (166K to 195K) for AIME, where each solver completion
is long. Solver output shown to the optimizer is cut to its last 400 characters; the implementation notes record that uncapped AIME
completions could exceed the deployment's per-minute token quota. Optimizer cost for the GPT-4.1 Mini AIME runs was about \$0.63 to \$0.68.
\finding Showing everything fits in one request here, but it is the main reason the design does not obviously scale to large
training sets, where sampling would be needed.

\subsection{Validation items as feedback, and its cost}
\label{app:d6}

$f$ so that expected per-round churn equals the observed mean of 10.8\% of validation items (52 committed rounds) gives $f=0.26$; $f=1$
corresponds to independent re-evaluations.

\subsection{Number of rounds}
\label{app:d7}
We use three rounds. Among the 11 runs with a unique best-validation round, the best was round 1 twice, round 2 six times, and round 3 three
times, so rounds 2 and 3 matter, but we did not run more than three rounds, and each additional round costs one optimizer call and two
solver passes.

\subsection{Settings we did not ablate}
\label{app:d8}
Optimizer temperature 0.7, the 95\% skip threshold, the validation fraction (0.5, and 0.35 for AIME and IFBench with GPT-4.1 Mini), the 400-character output cap, the
five-section schema (inherited from prior work, \S\ref{sec:related}), and seed 0 were fixed from the start or chosen by inspection. We did not tune them against test results to our knowledge, but we did not log a pre-registration, so this is a statement of
intent rather than a verifiable guarantee. Their effect is unmeasured.

\paragraph{Why the final design looks the way it does.} Three lessons carried through. First, evaluation noise is large relative to the
effects we study: the same prompt scored differently on identical test items across runs, which is why the paper reports item counts
rather than percentages alone and treats the AIME results as inconclusive. Second, any quantity the optimizer can see will be optimistic
as an estimate of generalization, whether it is the mining set (phase 3) or, as we show in \S\ref{sec:valtest}, the validation set
itself. Third, an optimizer that is allowed to ship a regression will do so on near-ceiling tasks (phase 4). We responded with a skip
threshold and unconditional commits plus best-validation selection, not with a gate against the seed, so the shipped prompt can still
score below the seed on validation (two of 16 eligible non-AIME shipped runs); the paper reports this rather than hiding it.

\section{Mechanism History}
\label{app:history}
The final mechanism is the product of three earlier designs, each abandoned for a measured reason. An
early section-local design, in which an LLM judge attributed each failure to one prompt section before a scoped
edit, was retired because attribution was noisy and a strict regression gate rejected over 40\% of proposed edits
with no clear improvement trend. A whole-prompt design using exact-substring find/replace edits was retired after a mean
effect indistinguishable from zero across repeated seeds, a gate that rejected net-positive trades, and
round-to-round oscillation rather than compounding gains. An intermediate design that encouraged ``worked examples''
in the rewritten prompt caused the optimizer to paste training items nearly verbatim; test accuracy fell by 6.8 points
until an explicit anti-copying instruction was added, which the final optimizer prompt retains.

\subsection{Evaluation noise}
\label{app:noise}
Item-level traces reveal variation even when aggregate scores agree. On IFBench, two GPT-4o-mini runs with identical configuration ended at the same
aggregate (47.6 $\rightarrow$ 45.2) but with different item sets: 2 recovered/3 regressed in one, 0/1 in the other. On AIME with GPT-4.1

$\rightarrow$ 53.3 pair selected from the summary for Table~\ref{tab:main}. These rechecks do not verify that pair or
measure a fixed-harness noise floor. Proper controls must repeat seed and candidate with identical caps, labels,
item IDs, model versions, and scoring settings.

\subsection{What the tracking caught in our own harness}
\label{app:bugs}
\paragraph{PUPA judge truncation.}
The PUPA quality judge is a reasoning model whose completions were being silently truncated by a hard-coded token cap unrelated to the
experiment's solver budget; truncated calls defaulted to a quality score of zero. The item-level trace flagged a pattern of validation
regressions that did not correspond to any difference in prompt content, and following the affected items back to the judge's token
usage located the cap. After the fix, GPT-4.1 Mini's PUPA composite rose from 68.2 to 80.7 with 10 test items recovered and none
regressed.

\paragraph{IFBench checker and stale optimizer instruction.}
A regression the trace marked as suspicious led us to a constraint rule (\texttt{words:no\_consecutive}) that checked a different
condition than the one stated in the instruction text. A separate audit found an optimizer instruction that no longer matched the
round-selection logic. After fixing both, IFBench with GPT-4.1 Mini moved from 42.9 to 66.7 (12 recovered, 2 regressed). The
GPT-4o-mini IFBench and PUPA runs predate these fixes, so Table~\ref{tab:main} should be compared within a solver, not across solvers.

\section{Evaluation Details}
\label{app:eval}
Answer extraction and scoring are programmatic for every benchmark; the only model-scored quantity is PUPA's response quality.
\begin{itemize}
\item \textbf{MMLU and Hearsay.} The solver ends with a line of the form \texttt{Answer: <letter>} (MMLU) or
\texttt{Answer: Yes/No} (Hearsay), which is extracted and compared with the gold label. The prompt may ask for visible
reasoning before that line.
\item \textbf{AIME.} The solver writes the final integer (0 to 999) on its own line as \texttt{\#\#\#\# <number>}; scoring is exact match.
\item \textbf{IFBench.} Programmatic verifiers check each instruction in an item; an item counts as correct only if
every instruction is satisfied. Our verifier implements 32 of the 83 constraint types in the two benchmarks combined.
Results are for the supported subset under our checker, not certified full-benchmark official accuracy; unsupported
constraints and provider-blocked items require explicit exclusion records.
\item \textbf{PUPA.} A three-step pipeline. (1) The solver, using the optimized prompt, rewrites the private user query into a
redacted request. (2) A fixed external model (GPT-4.1) answers the redacted request. (3) The solver, using a fixed synthesis
instruction, combines the external answer with the original query into the final response. Leakage is the fraction of annotated
PII strings found in the redacted request (string matching, no model call). Quality is a GPT-5 judge's 0 to 1 score of the final
response against the dataset's reference response (judge completions are allowed 4096 tokens after the fix in
Appendix~\ref{app:bugs}). The composite is $(\text{quality}+(1-\text{leakage}))/2$; recovered/regressed use the threshold 0.7. Only the
step-1 prompt is optimized.
\item \textbf{Content filter.} Items whose call is refused by the provider's content filter are excluded from the denominator,
not scored as wrong: 2 of 40 PUPA test items and 3 of 66 MMLU professional-law test items, identically for both solvers.
Before/after transition accounting requires common evaluated IDs, not just equal denominator sizes. Excluding refusals
conditions the result on answerability and may bias estimates; no all-items refusal-as-failure sensitivity analysis is reported.
\end{itemize}

\section{Optimizer Instructions and Seed Prompt}
\label{app:prompts}
\paragraph{Optimizer system prompt.} One template serves every benchmark; only the task description and the round budget $N$
change. In order, it tells the optimizer: (i) this is a measured multi-round experiment with at most $N$ rewrites; (ii) from round 2
it is shown the measured effect of its previous rewrite, in full, on both the mining and validation sets, and should first
diagnose which of its edits caused which recoveries and regressions, then keep what recovered items and revert or repair what
regressed them; (iii) the shipping rule, quoted below; (iv) a rule against turning shown items into examples, quoted below;
(v) that the solver has no hidden scratchpad, so reasoning helps only if written out, and that reasoning tasks differ from pure
recall tasks; (vi) the fixed five-section schema and the required final answer line; and (vii) that it may begin with an
\texttt{\#\# Analysis} section, which the parser discards.

\begin{quote}\small
Shipping rule: ``Every round commits unconditionally to a version history, and at the end, whichever COMMITTED round scores BEST
on validation accuracy is the one that actually ships [...] Validation accuracy is therefore not just a diagnostic number: it is
literally the criterion your rewrite is competing on.''
\end{quote}
\begin{quote}\small
Example rule: ``you are shown every failure, every success, and every validation item so you can DIAGNOSE what is going wrong,
NOT so you can turn them into illustrative examples.''
\end{quote}
The quoted shipping rule is from the current version. The nine runs that shipped the final round (\S\ref{sec:method}) used an
earlier version that instead said there is no best-round selection and that the last round ships; validation accuracy was reported
to the optimizer as a diagnostic only. In the archived optimized runs, flipped validation items were shown in full
from the next rewrite onward; this does not establish a mapping for the replacement AIME summary.

\paragraph{Effect report.} From round 2 the user message contains: the previous text of every section the optimizer changed;
every mining item its rewrite recovered (question and gold answer); every mining item it regressed (question, the solver's new
wrong answer truncated to its last 400 characters, and the gold answer); the validation accuracy before and after; and the same
two lists for validation items. It ends with an instruction to diagnose causes on both sets before rewriting.

\paragraph{Full optimizer system prompt.} The text below is the template used for every reported run that shipped under the
best-validation rule; \texttt{\{task\_description\}} and \texttt{\{max\_rounds\}} are filled per benchmark and run. Line breaks
are reflowed and the source's ASCII arrows are typeset as $\rightarrow$; the wording is unchanged.
Assertions about a solver's ``hidden scratchpad'' and reliable reasoning gains below are instructions in the experimental
template, not verified architectural facts or conclusions of this paper. Requests to diagnose causes do not turn
observational transitions into causal evidence.

\begin{promptbox}[title={\textbf{Optimizer system prompt} (reflect mode, current version)}]{softblue}
You are working with an expert prompt engineer to help a smaller LLM (the ``solver'') solve \texttt{\{task\_description\}} more
reliably.\par\medskip
\textbf{HOW THIS PROCESS WORKS} (read carefully -- this is a measured, multi-round experiment, not a one-shot rewrite):\par
\noindent 1. You get up to \texttt{\{max\_rounds\}} rewrite rounds. After each round, your rewritten prompt is run on a WORKING SET of
examples and on a VALIDATION set -- a second, disjoint batch meant to approximate unseen data.\par
\noindent 2. From round 2 on, you are shown the measured EFFECT of your previous rewrite, IN FULL, on BOTH sets: every working-set item it
RECOVERED (wrong $\rightarrow$ right), every item it REGRESSED (right $\rightarrow$ wrong) together with the solver's new wrong answer,
the previous text of every section you changed, and -- just as fully -- every VALIDATION item it recovered and every validation item it
regressed, with the same detail. Nothing about validation is held back from you.\par
\noindent 3. In those later rounds your job is causal: first diagnose WHICH of your previous edits caused WHICH regressions and
recoveries on EITHER set, then rewrite -- keep the edits that recovered items, revert or repair the edits that regressed items, and
address the remaining failures. Do not churn wording that was not implicated by the evidence.\par
\noindent 4. There is no ``last round always ships'' rule. Every round commits unconditionally to a version history, and at the end,
whichever COMMITTED round scores BEST on validation accuracy is the one that actually ships -- not necessarily the last round, and not
necessarily this one. Validation accuracy is therefore not just a diagnostic number: it is literally the criterion your rewrite is
competing on. Treat every round as a real, standalone candidate for shipping, not a throwaway step toward some final round.\par
\noindent 5. Because you now see every validation item that flips, a rewrite that merely patches the specific items shown -- without
addressing the underlying rule that produced them -- will look good this round and can still fail on the next genuinely new case.
Prefer fixing the general rule that explains the failures over specific patches to the exact items shown.\par\medskip
You will see: the solver's current markdown-formatted prompt; (from round 2) the EFFECT REPORT of your previous rewrite described above;
EVERY question the solver currently gets wrong on the working set, with the solver's answer and the correct answer alongside (not a
sample -- all of them); and EVERY question the current prompt already gets right on the working set (not a sample -- all of them), so you
know exactly what must not break.\par\medskip
\textbf{CRITICAL RULE ABOUT EXAMPLES} -- READ BEFORE WRITING ANYTHING: you are shown every failure, every success, and every validation
item so you can DIAGNOSE what is going wrong, NOT so you can turn them into illustrative examples. When you write an invented example in
the Context or Task Details section: (a) Do NOT reuse the underlying scenario, fact pattern, or entities of ANY failure, gold, or
validation item shown to you in this conversation -- not verbatim, and not paraphrased with different names. Changing ``Linda and her
editors'' to ``Sarah and her colleagues'' is still copying; the solver pattern-matches on the STORY, not the names. (b) Before writing
an invented example, actively check: does this resemble the setup of anything I was just shown (a lab report, a bystander pointing, an
email admitting knowledge, a customer asking for a refund, someone hearing about a planned crime, a doctor's diagnosis, and so on)? If
yes, discard it and invent a genuinely different scenario. (c) Prefer stating the principle abstractly with NO example at all over
reusing a shown scenario's shape. An abstract rule generalizes; a disguised replay of a shown item does not -- it is memorization with a
different name attached, and it is exactly what causes a prompt to score well on the items you were shown and fail on the next genuinely
new one.\par\medskip
\textbf{CRITICAL FACT ABOUT THE SOLVER:} it has NO hidden scratchpad. Its ONLY reasoning space is the text it actually writes out. So
``think step by step'' works only if the solver WRITES the steps in its output, before the final answer line. Instructions like
``reason internally'', ``use a scratchpad but do not show it'', or ``output only the answer'' DESTROY the reasoning entirely -- for this
model they are identical to ``do not reason'', regardless of task type. Where a task does not need reasoning, the correct instruction is
to keep the answer direct -- never phrasings like these.\par\medskip
\textbf{FIRST, identify the task type from the failures you are shown:} (i) Reasoning tasks -- anything needing calculation, derivation,
formal logic, OR applying a rule/definition to a specific scenario (e.g. mathematics, econometrics, and hearsay / most legal analysis):
the solver RELIABLY does better when it WRITES OUT its working step by step before the final answer line. A bare answer starves it.
(ii) Pure factual-recall / lookup tasks -- where the answer is simply known or not, with no intermediate steps (e.g. a memorised
definition or fact): forced step-by-step reasoning can make the solver over-think and second-guess a fact it already recalled, LOWERING
accuracy. Sharpen the definitions and framing instead, and keep the answer direct. When unsure which it is, ALLOW visible reasoning --
it helps more often than it hurts, and the final answer line is extracted either way. Match your rewrite to the task type before doing
anything else.\par\medskip
\textbf{A good rewrite:} surfaces the general reasoning principle that separates correct from incorrect answers on this task, and states
it in terms the solver can apply to any new case it has not seen before; gives the solver the mental scaffolding it needs -- a clearer
way to think about the problem, a checklist, a decision procedure, a definition it can lean on; illustrates principles with GENUINELY
INVENTED examples when helpful -- different scenario, different entities, different setup from anything you were shown -- or no example
at all; keeps the fixed markdown schema (\texttt{\#\# System Role}, Context, Task Details, Constraints, Output Format), where you may
edit any section but must not add or remove these headers; keeps the FINAL answer line's format exactly (e.g. a line
\texttt{Answer: <LETTER>} or \texttt{Answer: Yes/No}), which is ALL the scorer reads and is searched for anywhere in the output, so you
MAY, and for reasoning tasks SHOULD, let the solver write visible step-by-step working BEFORE it (NEVER add ``output only the answer'',
``do not show your working'', or ``reason internally''); and MATCHES the reasoning style to the task type, with the objective being
accuracy, never verbosity for its own sake.\par\medskip
\textbf{RESPONSE FORMAT:} you MAY begin your reply with a short \texttt{\#\# Analysis} section (2-6 sentences diagnosing which previous
edit caused which regression or recovery -- state the cause before the fix; in round 1 you may use it to state your hypothesis instead).
The \texttt{\#\# Analysis} section is discarded automatically by the parser. After it, output the full rewritten markdown with the five
standard section headers. No other prose, no code fences, nothing after the last section.
\end{promptbox}

\paragraph{Per-iteration user message.} Each call also carries a user message that begins with an iteration note (``This is refinement
round $t$ of $N$ \ldots treat this rewrite as a real, standalone candidate for shipping''), followed by the current full prompt in a
fenced block, the effect report (from round 2), every working-set failure with the solver's output (last 400 characters) and the gold
answer, every correctly solved working-set item with its gold answer, and a closing request to rewrite the markdown.

\paragraph{Task descriptions.} \texttt{\{task\_description\}} is one fixed sentence per benchmark, written without error-mode hints:

\begin{promptbox}[title={\textbf{Task descriptions inserted into the system prompt}}]{softgreen}
\textbf{Hearsay.} a binary hearsay classification task under U.S. Federal Rule of Evidence 801 (deciding whether a courtroom statement is
hearsay). The output is Yes or No.\par
\textbf{MMLU.} a 4-way multiple-choice exam question (options A, B, C, D) from one academic subject. Computational subjects (mathematics,
econometrics) need multi-step working; factual-recall subjects (law, computer security, and similar) are usually answered best directly,
without forced step-by-step reasoning. The final answer is a single letter A, B, C, or D on an ``Answer:'' line.\par
\textbf{AIME.} a competition-level (AIME) math problem, substantially harder than grade-school word problems -- multi-step algebra,
combinatorics, number theory, geometry, or probability. The correct answer is always a specific integer between 0 and 999. The output
must end with a line containing the final numeric answer.\par
\textbf{IFBench.} an instruction-following task with the same mechanically verifiable constraint structure and the same
\texttt{FINAL RESPONSE:} marker convention as IFEval, but drawn from a broader set of constraint types (word/consonant/vowel counts,
keyword-frequency and forbidden-word rules, formatting requirements, and more). Correctness means the text after the marker satisfies
every listed constraint; there is no single gold answer to match. \emph{(In the code this description refers to the IFEval description, which
adds that the solver may plan before the marker and that guidance should stay general and concise rather than grow into a per-rule checklist.)}\par
\textbf{PUPA.} a privacy-conscious query-rewriting task: the input is a PRIVATE user request (may contain names, contact info, employers, or
other personal details). You are ONLY editing the REWRITE instruction -- the prompt that tells a model how to anonymize/generalize the
request before it is sent to a separate, untrusted external model. You are NOT editing how the final answer to the user is composed; that
step is fixed elsewhere. A failure means the rewritten request still leaked one or more specific private details (shown to you as
``leaked $N/M$ PII units'') -- the fix is to make the rewrite instruction more systematic about generalizing/abstracting every private
detail (names $\rightarrow$ roles, specific employers $\rightarrow$ generic descriptions, exact locations $\rightarrow$ broader regions,
etc.) while still preserving enough of the request's substance that the external model's answer stays useful. The ``gold''/quality signal
shown to you reflects the FINAL answer's usefulness (not directly under your control), so do not sacrifice the request's meaning purely to
hide details -- an unusable rewrite scores just as badly as a leaky one.
\end{promptbox}

\section{Prompt Evolution: Before and After}
\label{app:evolution}
The seed and shipped prompts below are copied from the saved run for LegalBench-Hearsay with GPT-4.1 Mini (seed 0, three
rounds). On this run validation accuracy rose from 76.0 to 96.0 and the sealed-test score from 71.4 to 73.5 (7 items recovered,
6 regressed; Table~\ref{tab:main}). The optimizer left the System Role and Output Format sections unchanged and rewrote the other three,
mostly Task Details, which grew from one sentence into a six-step decision procedure. Per-round section edits for every run are in
Table~\ref{tab:rounds}, and the seed and final prompts of every run are released with the traces.

\begin{promptbox}[title={\textbf{Before} (seed prompt $p_0$)}]{softblue}
\textbf{System Role.} You are a U.S. evidence-law expert.\par
\textbf{Context.} Hearsay is an out-of-court statement offered to prove the truth of the matter asserted.\par
\textbf{Task Details.} Decide whether the given statement is hearsay.\par
\textbf{Constraints.} Apply the definition strictly; conduct is not hearsay unless it is assertive.\par
\textbf{Output Format.} End your response with a line in exactly this form: Answer: Yes (or) Answer: No
\end{promptbox}

\begin{promptbox}[title={\textbf{After} (shipped prompt $p^*$)}]{softgreen}
\textbf{System Role.} You are a U.S. evidence-law expert. \emph{(unchanged)}\par
\textbf{Context.} Hearsay is an out-of-court statement offered to prove the truth of the matter asserted. A ``statement'' includes
oral/written assertions and assertive conduct. The key is whether the relevance of the evidence depends on accepting as true what the
statement asserts (including any embedded or intermediate assertion that must be true for relevance).\par
\textbf{Task Details.} Decide whether the given statement is hearsay by applying this decision procedure and explain your steps
briefly before the final answer:\par
\textit{Step 1.} Is there a ``statement''? Identify whether the evidence is an assertion (oral/written) or assertive conduct.
Non-assertive words (questions, commands, offers) and non-assertive conduct are not statements.\par
\textit{Step 2.} Was it made out of court? In-court testimony in this proceeding is not hearsay for this purpose.\par
\textit{Step 3.} What specific proposition is the evidence offered to prove (ultimate or intermediate)? Then apply the independent
relevance test: would the evidence still be probative of that proposition even if the content of the statement were false? If yes, it
is offered for a non-truth purpose; if no, it is offered for its truth.\par
\textit{Step 4.} If the evidence is offered solely for a non-truth purpose, answer No. Common non-truth purposes: effect on the listener,
notice, knowledge or motive where only the hearing of the words matters; proving that a conversation or words occurred; and
circumstantial use of words to show a condition or state of the speaker unrelated to their truth.\par
\textit{Step 5 (guardrail on embedded assertions).} If the proponent relies on the statement to establish an intermediate fact that
itself depends on the truth of an asserted proposition within it (e.g., ``I heard/know/saw X''), the statement is used for its
truth; treat as hearsay. Do not invoke the guardrail when the use is only to show that words were spoken, the speaker's state, or an
effect on the listener where content truth is irrelevant under Step 3.\par
\textit{Step 6.} If out-of-court and offered for the truth of what it asserts, answer Yes; otherwise answer No.\par
\textbf{Constraints.} Apply the definition strictly; do not consider exclusions or exceptions (e.g., party-opponent statements or hearsay
exceptions). Conduct is not hearsay unless intended as an assertion. Questions, commands, and other non-assertions are not hearsay.
Keep explanations concise and focused on the steps.\par
\textbf{Output Format.} \emph{(unchanged)}
\end{promptbox}

sealed-test score moved by one item (36 instead of 35 of 49 correct), with 13 items changing in either direction. The optimizer had
seen the validation items this prompt was selected on, so a large validation gain and a near-flat test result can coexist for the same
prompt text.

\finding On this run the optimizer added visible planning and a verification checklist, and the test score rose by 10 items net. The same
schema and optimizer produced a prompt that did not help GPT-4o-mini on this benchmark ($-2.4$; that run predates the harness fixes,
so the comparison is not clean), so we do not attribute the improvement to the prompt text alone.

\section{Artifact Provenance and Release Plan}
\label{app:artifacts}
The working repository stores configurations, \texttt{metrics.json}, evaluation logs, token/cost ledgers, baseline/current
prompts, and round registries. These files are not automatically a privacy-safe anonymous release: evaluation logs
include predictions and gold text, and prompts can contain examples. The intended review bundle is limited to sanitized
configuration and prompt files, per-item IDs/outcomes, transition counts, costs, and analysis scripts; publication of an
audited anonymous archive is not verified here.

\texttt{reported\_results.json} records the supplied headline values, denominators, author-confirmed transition counts, and
provenance status. \texttt{val\_test\_gap.json} preserves archived matched accuracy records; analysis excludes its AIME
entries rather than replacing their test scores while retaining unrelated validation scores. The overlap and design
artifacts describe their archived prompt collection. Matching run IDs, prompt hashes, and per-item logs for the two
supplied AIME gains are still required before those gains can support a reproducibility claim.
