\title{Beyond Aggregate Accuracy: Item-Level Transitions in Prompt Optimization}

\begin{abstract}
Automatic prompt optimization (APO) revises the natural-language instructions that configure language-model systems
using feedback from model outputs, yet it is evaluated almost exclusively by aggregate before/after scores. Such scores
hide which cases each revision fixes and which it breaks. We introduce Reflective Feedback-Driven Prompt Optimization
(RFDPO), an auditable prompt optimizer that returns the item-level effect of each edit to the optimizer and records, at
every revision, the prompt version, paired recoveries and regressions on tuning and test data, and per-role token cost.
Across five benchmarks and two solver models, aggregate scores substantially understate behavioral change: on
LegalBench-Hearsay, single-item net changes conceal 13--17 changed outcomes, and in five configurations the number of
changed outcomes is at least five times the net change. Validation gains average 7.9 points, against 4.8 points on
held-out test items. Across rounds the optimizer narrows its edits from 4.3 of five prompt sections to 1.3, yet later
rounds still break nearly as many items as they fix. In a controlled ablation on LegalBench-Hearsay (five runs per
arm), the item-level effect report leaves the net gain unchanged but cuts the items that flip per round by 40\%. We
argue that recovery, regression, churn, and tuning-to-test transfer should be standard reporting dimensions for APO.
\end{abstract}

\section{Introduction}
\label{sec:intro}

\centering

\label{fig:arch}

Language models are used to classify documents, extract information, answer questions, and follow instructions.
These systems can be configured with a \emph{prompt}: natural-language instructions supplied alongside the task input
to describe the task, relevant context, constraints, and response format. For example, an extraction prompt can specify
which fields to return and how to represent missing values. Small changes in wording or formatting can substantially
affect performance without changing model parameters~\citep{sclar2024quantifying}.

Manual prompt refinement alternates between editing instructions and evaluating outputs.
\emph{Automatic prompt optimization} (APO) automates this search~\citep{zhou2023ape,yang2024opro,pryzant2023protegi}.
In LLM-based approaches, a \emph{solver} performs the task while an \emph{optimizer} receives the current prompt and
evaluation feedback and proposes a revision. Candidate outputs or scores inform subsequent rewrites; solver parameters
remain fixed. These are distinct roles, not necessarily different model architectures. Here, GPT-5 rewrites prompts
for GPT-4o-mini and GPT-4.1 Mini solvers.

For an engineer refining document extraction or retrieval-augmented question answering, where retrieved documents
accompany a query~\citep{lewis2020rag}, the consequences of each edit matter: which failing cases now work, which correct
cases break, and which failures remain. \textbf{These observations can inform the next edit.} APO methods inspect
failures or execution traces to propose revisions, yet they are typically reported through aggregate before/after
scores that hide these transitions. The cost of hidden transitions is documented for deployed LLM applications: across
hosted-API updates for toxicity detection, 10.9\% of individual predictions regressed, and when overall accuracy
improved, at least one previously correct prediction broke in 87.9\% of cases~\citep{ma2024regression}. Developers likewise
report that debugging LLM behavior that is inconsistent across prompt variations is difficult~\citep{errica2025wrong}. A
prompt revision that raises a score while breaking previously correct cases can silently undo behavior that users and
downstream tests rely on.

A net gain of two items, for example, can mean two corrections with no regressions or ten corrections offset by eight
regressions. The scores agree, but the changes warrant different inspection. On the small evaluation sets often used
in prompt optimization, near-flat accuracy can conceal substantial movement between correct and incorrect outcomes
(\S\ref{sec:results}).

A second question is \textbf{whether gains generalize}. Candidates are often compared on a \emph{validation set} whose
examples may also provide optimizer feedback, and improvement on such tuning examples need not transfer to unseen
data~\citep{recht2019imagenet}.

We track \emph{recoveries} (incorrect to correct), \emph{regressions} (correct to incorrect), and \emph{churn} (all
changed outcomes) at every revision, and we feed them back into optimization. \emph{Reflective Feedback-Driven Prompt
Optimization} (RFDPO) is an auditable prompt optimizer (Figure~\ref{fig:arch}). From its second round, the optimizer sees
which items its own previous edit recovered and which it regressed, with the solver's new outputs and the text the edit
replaced, on both tuning sets. Existing optimizers condition on scored prompt histories or on the current candidate's
errors or traces, or use regressions only to accept or reject a candidate (\S\ref{sec:related}); RFDPO returns the
item-level consequences of an edit to the editor. It also versions every prompt and meters token use and cost by role,
so each revision can be audited. A controlled ablation shows what the report changes: at equal net gain, it cuts the
items that flip per round by 40\% (\S\ref{sec:edits}).

We apply RFDPO to LegalBench-Hearsay, MMLU, IFBench, AIME, and PUPA with GPT-4o-mini and GPT-4.1 Mini solvers and ask
what paired outcomes reveal beyond aggregate scores; test examples never enter optimizer feedback or candidate
selection. To our knowledge, no prior APO work returns the item-level effect of an edit to the optimizer or tracks
paired transitions across revisions on tuning and test data. Our contributions are:

\begin{itemize}\setlength{\itemsep}{2pt}\setlength{\parskip}{0pt}\setlength{\topsep}{2pt}
\item \textbf{An auditable reflective optimizer.} RFDPO returns the item-level effect of each edit to the optimizer and
records prompt versions, paired transitions on tuning and test data, and per-role token cost at every revision
(\S\ref{sec:method}).
\item \textbf{Evidence that aggregate scores hide behavioral change.} Across five benchmarks, a one-item net change can
conceal 17 changed outcomes, and held-out test gains reach about three-fifths of validation gains (\S\ref{sec:results}).
\item \textbf{A characterization of reflective editing.} Across rounds, the optimizer shifts from rewriting
most of the prompt to edits of about one section while regressions persist (\S\ref{sec:edits}); we derive reporting practices
for APO from these findings (\S\ref{sec:discussion}).
\end{itemize}

Together, these observations motivate treating recovery, regression, churn, and validation-to-test transfer as
\textbf{first-class reporting dimensions for APO}, alongside aggregate accuracy.

\section{Related Work}
\label{sec:related}

\paragraph{Prompt optimization.}
APO has progressed from discrete token-level search~\citep{shin2020autoprompt}
and generate-and-score instruction search~\citep{zhou2023ape}, to LLMs used as
optimizers over trajectories of scored prompts~\citep{yang2024opro}, textual-gradient
edits~\citep{pryzant2023protegi,yuksekgonul2025textgrad}, evolutionary
search~\citep{guo2024evoprompt,fernando2024promptbreeder}, and multi-stage pipelines
optimized jointly over instructions and demonstrations~\citep{opsahlong2024miprov2,schnabel2024sammo}, many of them packaged in
programming frameworks such as DSPy~\citep{khattab2024dspy}.
Closest to our prompt schema is MPO~\citep{sharma2026mpo}, which decomposes a prompt into the same five semantic sections
and applies additive, de-duplicated section-local textual gradients. GEPA~\citep{agrawal2026gepa} combines reflective
prompt mutation with Pareto-based selection over a population of prompts, and Trace2Policy~\citep{zha2026trace2policy}
refines a rule document by clustering errors and committing patches that pass a regression gate. General self-feedback
methods return verbal critiques to the model that produced an output~\citep{madaan2023selfrefine,shinn2023reflexion}.
These optimizers condition on scored prompt histories (OPRO), on the current candidate's errors or traces (ProTeGi,
GEPA), or use regressions to accept or reject a candidate (Trace2Policy). RFDPO instead returns to the optimizer the
measured, item-level consequences of its own previous edit: what it fixed, what it broke, and the text it replaced.

\paragraph{Published results use different protocols.}
Shared benchmark names do not imply comparable evaluations. Prior systems differ in resplitting, solver, baseline
instructions, feedback source, and repeated-evaluation budget. For example, GEPA's AIME baseline is a DSPy
chain-of-thought module, whereas ours is a five-section task prompt. Appendix~\ref{app:prior}, Table~\ref{tab:prior},
documents the protocol differences. Our question is what transition records reveal within each configuration rather
than which optimizer has the highest published score.

\paragraph{Evaluation beyond accuracy.}
Paired binary-outcome tables are classical~\citep{mcnemar1947sampling}. In model updating, negative flips, cases the old
model classifies correctly and the new one does not, motivate regression-free training~\citep{yan2021positive}. For LLM
applications, \citet{ma2024regression} argue that regression testing is needed because silent API updates can break
prompts that previously worked. Our regressions apply the same definition to prompt revisions, where they have not been
tracked across optimization trajectories. Work on prompt robustness makes a related point: small prompt perturbations
can flip a model's answers~\citep{salinas2024butterfly}, and sensitivity and consistency metrics complement task
accuracy as diagnostics for prompt engineering~\citep{errica2025wrong}. These measures capture variation across
rephrasings of a prompt, whereas we track labeled recoveries and regressions between deliberately edited prompt
versions. Because some apparent sensitivity reflects evaluation artifacts~\citep{hua2025flaw}, we define regressions
through each benchmark's scoring rule (\S\ref{sec:metric}). CheckList~\citep{ribeiro2020checklist} likewise shows that aggregate accuracy misses important behaviors of
a fixed model, and held-out accuracy can fall on fresh samples~\citep{recht2019imagenet}, which motivates measuring
tuning-to-test transfer item by item. \citet{oren2023proving} detect test-set contamination in black-box language
models; we check returned prompts for verbatim dataset overlap (\S\ref{sec:valtest}).

\paragraph{Test-set exposure.}
Trace2Policy reports a refinement round informed by errors on its held-out set~\citep{zha2026trace2policy}. Whether
evaluation items reach the optimizer strongly affects reported gains: in a diagnostic run (Appendix~\ref{app:oracle}),
supplying the test items as feedback raised test accuracy from 68.8\% to 95.3\%, against 73.4\% with the items held
out. RFDPO keeps test items out of feedback and selection.

\section{RFDPO}
\label{sec:method}

We introduce Reflective Feedback-Driven Prompt Optimization (RFDPO) that uses item-level evaluation outcomes to guide prompt revisions. RFDPO extends conventional feedback-driven optimization by explicitly identifying examples that become correct or incorrect after each revision and returning these changes to the optimizer. Figure~\ref{fig:arch} illustrates the overall workflow.

\subsection{Prompt Representation and Evaluation}

RFDPO uses a solver LLM to execute tasks and an optimizer LLM to revise prompts, without modifying the solver's parameters. Following MPO~\citep{sharma2026mpo}, each prompt contains five sections: System Role, Context, Task Details, Constraints, and Output Format. These sections remain fixed throughout optimization, allowing RFDPO to track which parts of a prompt are modified.

The tool operates on three disjoint sets: mining ($M$), validation ($V$), and test ($T$). Mining examples provide feedback for prompt revisions, while validation examples are used for candidate selection and, from the second round, also contribute feedback. The test set is excluded from optimization and evaluated only with the initial and returned prompts.

\subsection{Item-Level Transition Tracking}
\label{sec:metric}

RFDPO measures the effect of each revision by comparing example-level correctness before and after an edit. Let $c_i(p)\in\{0,1\}$ denote the observed correctness of example $i$ under prompt $p$. Given two prompts $p$ and $q$ evaluated on the same example set $D$, we define the recovered ($R$) and regressed ($G$) examples as

\begin{equation}
R=\{i\in D:c_i(p)=0,\ c_i(q)=1\},
\end{equation}
\begin{equation}
G=\{i\in D:c_i(p)=1,\ c_i(q)=0\}.
\end{equation}

We further define the net change $N$ and churn $C$ as

\begin{equation}
N=|R|-|G|,\qquad C=|R|+|G|.
\end{equation}

The net change corresponds to $|D|$ times the accuracy difference, whereas churn captures the total number of examples whose correctness changes. Thus, revisions with the same accuracy change may exhibit substantially different recovery and regression patterns, as illustrated in Figure~\ref{fig:metric}.

\begin{figure}[!t]
\centering
\includegraphics[width=\columnwidth]{figures/fig_metric.pdf}
\caption{Example of item-level transitions. Three examples are recovered and two regress, producing a net gain of one correct example and a churn of five.}
\label{fig:metric}
\end{figure}

Transitions are measured between consecutive revisions on $M$ and $V$, and between the initial and returned prompts on $T$, using matched evaluable example IDs.

\subsection{Feedback-Driven Prompt Revision}
\label{sec:optimization}

Algorithm~\ref{alg:reflect} presents the RFDPO optimization procedure. The solver first evaluates the initial prompt, and the optimizer generates a revision using the observed outcomes. From the second round, the optimizer additionally receives the recoveries and regressions caused by the preceding revision on $M$ and $V$, together with the affected questions, solver responses, gold answers, previous text of modified sections, and validation accuracy changes.

Each valid, changed candidate is evaluated and committed as the starting point for the next round, even if its validation accuracy decreases. This allows subsequent revisions to build on earlier edits without a regression-based acceptance gate.

Under best-validation selection, RFDPO returns the committed candidate with the highest validation accuracy, breaking ties by mining accuracy and candidate order. Once a candidate is committed, the seed is not reconsidered; if no candidate is committed, the seed is retained.

RFDPO also records prompt versions, modified sections, item-level outcomes, and model-call token usage and costs. These records support analysis of optimization trajectories, behavioral changes, and resource consumption.

\begin{algorithm}[!t]
\caption{RFDPO optimization with edit-effect feedback}
\label{alg:reflect}
\small
\begin{algorithmic}[1]
\Require seed $p_0$; disjoint $M,V,T$; $\textsc{Opt}$; $\textsc{Solve}$; round budget $B$
\State $s_0,v_0 \gets \textsc{Solve}(p_0,M),\ \textsc{Solve}(p_0,V)$
\State $\tau_0 \gets \textsc{Solve}(p_0,T)$ \Comment{baseline; measured only}
\State $\mathcal{H}\gets\emptyset$; $(p,s,v)\gets(p_0,s_0,v_0)$; $\rho\gets\emptyset$
\For{$t=1$ \textbf{to} $B$}
  \If{skip threshold reached, or no mining failures} \State \textbf{break} \EndIf
  \State $q\gets\textsc{Opt}(p,s,v,\rho)$ \Comment{mining items and feedback}
  \If{$q=p$} \State \textbf{continue} \EndIf
  \State $s',v'\gets\textsc{Solve}(q,M),\ \textsc{Solve}(q,V)$
  \State $\rho\gets((R,G)(s\!\to\!s'),(R,G)(v\!\to\!v'))$
  \State append $(q,s',v')$ to $\mathcal{H}$ \Comment{no regression gate}
  \State $(p,s,v)\gets(q,s',v')$
\EndFor
\State $p^*\gets p_0$ if $\mathcal{H}=\emptyset$; otherwise select from $\mathcal{H}$
\Statex \hspace{\algorithmicindent} by validation accuracy, then mining accuracy
\State $\tau^* \gets \textsc{Solve}(p^*,T)$ \Comment{measured only}
\State \Return $p^*$, and $(R,G)(\tau_0\!\to\!\tau^*;T)$
\end{algorithmic}
\end{algorithm}



\section{Experimental Setup}
\label{sec:setup}

We evaluate RFDPO across five benchmarks and two solver models, covering different task types, answer formats, and scoring criteria. Table~\ref{tab:setup} summarizes the benchmark configurations.

\subsection{Benchmarks}

\textbf{LegalBench-Hearsay}~\citep{guha2023legalbench} evaluates binary classification of statements under U.S. hearsay law.

\textbf{MMLU}~\citep{hendrycks2021mmlu} consists of four-way multiple-choice questions. We select six subjects: college mathematics, computer security, econometrics, high school biology, philosophy, and professional law, optimizing each independently and reporting macro-averaged accuracy.

\textbf{IFBench}~\citep{pyatkin2025ifbench} evaluates compliance with verifiable output constraints. An example is correct only when all applicable constraints are satisfied, using a programmatic verifier partly based on IFEval~\citep{zhou2023ifeval}.

\textbf{AIME}~\citep{maa2025aime} evaluates mathematical reasoning with integer answers between 0 and 999. We use problems from 2022--2024 for optimization and the 30 problems from 2025 for testing.

\textbf{PUPA}~\citep{li2025papillon} evaluates privacy-conscious delegation to an external LLM. We optimize only the query-redaction prompt. Correctness requires a composite score $(\mathrm{quality}+1-\mathrm{leakage})/2$ of at least $0.7$.

\subsection{Models and Experimental Protocol}

We use GPT-4o-mini~\citep{openai2024gpt4o} and GPT-4.1 Mini~\citep{openai2025gpt41} as solvers, both with temperature $0$, and GPT-5~\citep{openai2025gpt5} as the optimizer with temperature $0.7$. PUPA additionally uses a fixed GPT-4.1 external model and GPT-5 as its quality judge.

All experiments use seed $0$ and at most three optimization rounds. Optimization is skipped when initial mining accuracy reaches $95\%$, except for PUPA. Eight earlier GPT-4o-mini runs used final-round selection rather than the current best-validation selection rule.

The matched evaluation includes 19 baseline/final records: seven non-MMLU configurations and twelve independently optimized MMLU subjects. Both endpoints of each matched pair are evaluated within the same run. The separately retained GPT-4o-mini AIME summary is excluded from matched analyses.

We report test accuracy, validation accuracy changes, recovery, regression, and churn. We also examine revision-level transitions and recorded token consumption. Detailed run configurations, scoring procedures, and optimizer instructions are provided in Appendices~\ref{app:config}, \ref{app:eval}, and \ref{app:prompts}.

\paragraph{Verbatim overlap.}
We also checked whether returned prompts contained eight-word sequences copied from benchmark examples. Sixteen of the 19 prompts showed no such overlap. The remaining three contained either a generic mathematical phrase or a True/False answer template (Appendix~\ref{app:overlap}).

\subsection{Prompt Revision Behavior}
\label{sec:edits}

We analyze how the optimizer modifies prompts across successive rounds. In round 1, where no effect report of a previous edit is available, the optimizer modified an average of 4.3 of the five prompt sections, compared with 1.3 in rounds 2--3, where it receives recovery and regression feedback on its previous edit. Revisions thus became more localized after the initial round.

% Nevertheless, smaller edits did not eliminate regressions. Later rounds recovered 56 mining examples while regressing 54, compared with 59 recoveries and 27 regressions in round 1. This indicates that revisions continued to introduce new failures even when fewer prompt sections were modified.

\paragraph{Effect-report ablation.}
To distinguish the effect of feedback from that of the optimization round, we conducted a controlled ablation on LegalBench-Hearsay using GPT-4o-mini. Both conditions replayed the same round-1 prompt and continued through rounds 2 and 3, differing only in whether the optimizer received the item-level effect report. We performed five runs per condition (Appendix~\ref{app:ablation}).

Without the report, round-2 revisions already modified only 1.6 prompt sections on average, compared with 2.0 when the report was included. Thus, the reduction in edit scope cannot be attributed solely to item-level feedback.

However, the feedback affected the number of changed outcomes. With the report, an average of 3.1 mining examples changed correctness per round, compared with 5.2 without it ($p=0.024$, exact permutation test over runs). Both conditions achieved similar net gains of 0.3 and 0.2 mining examples per round, respectively.

On the test set, accuracy changed by $-5.3$ and $-5.7$ percentage points with and without the report, respectively. These results suggest that item-level feedback can reduce outcome churn in this setting, although the ablation does not demonstrate substantial improved test accuracy.

\section{Discussion}
\label{sec:discussion}

\paragraph{Understanding prompt revisions.}
Aggregate accuracy does not reveal which examples a prompt revision fixes or breaks. Recovery and regression tracking distinguishes newly corrected examples, newly introduced failures, and persistent errors. These transitions provide more specific feedback for subsequent revisions. Our results show that even small net accuracy changes can involve substantial changes in individual outcomes, highlighting the importance of examining both recovery and regression.

\paragraph{Effect of item-level feedback.}
Although later optimization rounds modify fewer prompt sections, the ablation indicates that this narrowing is largely associated with the optimization round rather than the effect report itself. However, providing item-level feedback reduced average mining-set churn from 5.2 to 3.1 items per round (approximately 40\%) while maintaining similar net gains. This suggests that feedback can help limit changes in example-level correctness without necessarily improving overall accuracy. The finding is limited to the evaluated Hearsay setting, where test accuracy did not improve.

\paragraph{Generalization to unseen examples.}
Validation examples also provide optimization feedback and therefore represent tuning data rather than independent evaluation. Across edited-prompt returns, average test improvements were approximately 61\% of average validation improvements, and four runs showed declining test accuracy despite validation gains. These findings emphasize the need to report validation and test changes separately rather than interpreting tuning improvements as evidence of generalization.

\paragraph{Reporting optimization behavior.}
Recovery, regression, and churn provide complementary information to aggregate accuracy and can be computed from existing item-level evaluations without additional solver calls. We recommend reporting these transitions alongside prompt versions, evaluation exclusions, and resource consumption. RFDPO records this information automatically, enabling inspection of prompt revisions and their associated costs. Its source accompanies this submission (Appendix~\ref{app:artifacts}).


\section{Conclusion}
Aggregate scores report the net result of prompt optimization but not the cases gained and lost. RFDPO returns the
item-level effect of each edit to the optimizer and records every transition, prompt version, and token it consumes.
Across five benchmarks, these records show that one-item net changes can conceal up to 17 changed outcomes, that
held-out test gains reach about three-fifths of validation gains, and that later rounds keep trading cases as edits
narrow; in a Hearsay ablation, the effect report cuts the items that flip per round by 40\% at equal net gain.
Recovery, regression, churn, and tuning-to-test transfer should become standard reporting
dimensions for APO.

\section*{Limitations}
\label{sec:limitations}
Each configuration is evaluated with a single seed, and the study uses two closed-weight solver models. We did not
evaluate open-weight solvers, which would have required GPU resources beyond our compute and budget. The effect-report
ablation uses one benchmark, LegalBench-Hearsay, with five independent runs per arm.

\section*{Ethical Considerations}
Data come from public benchmarks, resplit as described in Table~\ref{tab:setup}. PUPA contains personal information from
public user--LLM conversations. Hosted solver and optimizer APIs receive the original queries during evaluation and
feedback; redaction protects only the designated external model. String-matched leakage does not capture paraphrased or
inferred information. Released traces would contain item IDs and outcomes only, without raw inputs, predictions, or
gold text (Appendix~\ref{app:artifacts}).

\subsection{Scoring and Evaluable Items}
\label{app:eval}
\paragraph{Answer extraction.}
MMLU and Hearsay outputs are scored by extracting \texttt{Answer: <letter>} and \texttt{Answer: Yes/No}, respectively,
and comparing with the gold label. AIME uses exact integer match on \texttt{\#\#\#\# <number>} (0--999). Visible
reasoning before these answer markers is not itself scored. IFBench checks only the content following
\texttt{FINAL RESPONSE:}; an item passes when every supported constraint is satisfied. The verifier implements 32
of the 83 constraint types in IFEval and IFBench combined, and evaluated items use the supported types.

\paragraph{PUPA pipeline and metrics.}
The optimized solver prompt rewrites a private query into a redacted request. Fixed GPT-4.1 answers that request;
the solver then synthesizes a final answer under a fixed instruction, using the original query and external response.
Leakage is the fraction of annotated PII strings present in the redacted request. A GPT-5 judge scores final-answer
quality against the reference on a 0--1 scale, with up to 4,096 completion tokens. An item is correct when the
composite $(\text{quality}+1-\text{leakage})/2$ reaches 0.7; reported PUPA accuracy uses this criterion. Only the
rewrite prompt is optimized.

\paragraph{Denominators and accounting.}
Provider-blocked items are excluded rather than scored as incorrect: PUPA evaluates 38 of 40 test items and MMLU
professional law 63 of 66, identically for both solvers. Transitions are computed over common evaluated IDs, so
$\Delta\mathrm{acc}=(|R|-|G|)/|D|$ and $C=|R|+|G|=|N|+2\min(|R|,|G|)$; MMLU transitions sum subjects while its
accuracy is macro-averaged.

\subsection{Optimizer System Prompt}
\label{app:sysprompt}
\texttt{\{task\_description\}} and \texttt{\{max\_rounds\}} are filled per benchmark and run. The template's wording is
preserved, with reflowed lines and ASCII arrows typeset as $\rightarrow$.

\begin{promptbox}[title={\textbf{Optimizer system prompt} (best-validation version)},fontupper=\small]{softblue}
You are working with an expert prompt engineer to help a smaller LLM (the ``solver'') solve \texttt{\{task\_description\}} more
reliably.\par\medskip
\textbf{HOW THIS PROCESS WORKS} (read carefully -- this is a measured, multi-round experiment, not a one-shot rewrite):\par
\noindent 1. You get up to \texttt{\{max\_rounds\}} rewrite rounds. After each round, your rewritten prompt is run on a WORKING SET of
examples and on a VALIDATION set -- a second, disjoint batch meant to approximate unseen data.\par
\noindent 2. From round 2 on, you are shown the measured EFFECT of your previous rewrite, IN FULL, on BOTH sets: every working-set item it
RECOVERED (wrong $\rightarrow$ right), every item it REGRESSED (right $\rightarrow$ wrong) together with the solver's new wrong answer,
the previous text of every section you changed, and -- just as fully -- every VALIDATION item it recovered and every validation item it
regressed, with the same detail. Nothing about validation is held back from you.\par
\noindent 3. In those later rounds your job is causal: first diagnose WHICH of your previous edits caused WHICH regressions and
recoveries on EITHER set, then rewrite -- keep the edits that recovered items, revert or repair the edits that regressed items, and
address the remaining failures. Do not churn wording that was not implicated by the evidence.\par
\noindent 4. There is no ``last round always ships'' rule. Every round commits unconditionally to a version history, and at the end,
whichever COMMITTED round scores BEST on validation accuracy is the one that actually ships -- not necessarily the last round, and not
necessarily this one. Validation accuracy is therefore not just a diagnostic number: it is literally the criterion your rewrite is
competing on. Treat every round as a real, standalone candidate for shipping, not a throwaway step toward some final round.\par
\noindent 5. Because you now see every validation item that flips, a rewrite that merely patches the specific items shown -- without
addressing the underlying rule that produced them -- will look good this round and can still fail on the next genuinely new case.
Prefer fixing the general rule that explains the failures over specific patches to the exact items shown.\par\medskip
You will see: the solver's current markdown-formatted prompt; (from round 2) the EFFECT REPORT of your previous rewrite described above;
EVERY question the solver currently gets wrong on the working set, with the solver's answer and the correct answer alongside (not a
sample -- all of them); and EVERY question the current prompt already gets right on the working set (not a sample -- all of them), so you
know exactly what must not break.\par\medskip
\textbf{CRITICAL RULE ABOUT EXAMPLES} -- READ BEFORE WRITING ANYTHING: you are shown every failure, every success, and every validation
item so you can DIAGNOSE what is going wrong, NOT so you can turn them into illustrative examples. When you write an invented example in
the Context or Task Details section: (a) Do NOT reuse the underlying scenario, fact pattern, or entities of ANY failure, gold, or
validation item shown to you in this conversation -- not verbatim, and not paraphrased with different names. Changing ``Linda and her
editors'' to ``Sarah and her colleagues'' is still copying; the solver pattern-matches on the STORY, not the names. (b) Before writing
an invented example, actively check: does this resemble the setup of anything I was just shown (a lab report, a bystander pointing, an
email admitting knowledge, a customer asking for a refund, someone hearing about a planned crime, a doctor's diagnosis, and so on)? If
yes, discard it and invent a genuinely different scenario. (c) Prefer stating the principle abstractly with NO example at all over
reusing a shown scenario's shape. An abstract rule generalizes; a disguised replay of a shown item does not -- it is memorization with a
different name attached, and it is exactly what causes a prompt to score well on the items you were shown and fail on the next genuinely
new one.\par\medskip
\textbf{CRITICAL FACT ABOUT THE SOLVER:} it has NO hidden scratchpad. Its ONLY reasoning space is the text it actually writes out. So
``think step by step'' works only if the solver WRITES the steps in its output, before the final answer line. Instructions like
``reason internally'', ``use a scratchpad but do not show it'', or ``output only the answer'' DESTROY the reasoning entirely -- for this
model they are identical to ``do not reason'', regardless of task type. Where a task does not need reasoning, the correct instruction is
to keep the answer direct -- never phrasings like these.\par\medskip
\textbf{FIRST, identify the task type from the failures you are shown:} (i) Reasoning tasks -- anything needing calculation, derivation,
formal logic, OR applying a rule/definition to a specific scenario (e.g. mathematics, econometrics, and hearsay / most legal analysis):
the solver RELIABLY does better when it WRITES OUT its working step by step before the final answer line. A bare answer starves it.
(ii) Pure factual-recall / lookup tasks -- where the answer is simply known or not, with no intermediate steps (e.g. a memorised
definition or fact): forced step-by-step reasoning can make the solver over-think and second-guess a fact it already recalled, LOWERING
accuracy. Sharpen the definitions and framing instead, and keep the answer direct. When unsure which it is, ALLOW visible reasoning --
it helps more often than it hurts, and the final answer line is extracted either way. Match your rewrite to the task type before doing
anything else.\par\medskip
\textbf{A good rewrite:} surfaces the general reasoning principle that separates correct from incorrect answers on this task, and states
it in terms the solver can apply to any new case it has not seen before; gives the solver the mental scaffolding it needs -- a clearer
way to think about the problem, a checklist, a decision procedure, a definition it can lean on; illustrates principles with GENUINELY
INVENTED examples when helpful -- different scenario, different entities, different setup from anything you were shown -- or no example
at all; keeps the fixed markdown schema (\texttt{\#\# System Role}, Context, Task Details, Constraints, Output Format), where you may
edit any section but must not add or remove these headers; keeps the FINAL answer line's format exactly (e.g. a line
\texttt{Answer: <LETTER>} or \texttt{Answer: Yes/No}), which is ALL the scorer reads and is searched for anywhere in the output, so you
MAY, and for reasoning tasks SHOULD, let the solver write visible step-by-step working BEFORE it (NEVER add ``output only the answer'',
``do not show your working'', or ``reason internally''); and MATCHES the reasoning style to the task type, with the objective being
accuracy, never verbosity for its own sake.\par\medskip
\textbf{RESPONSE FORMAT:} you MAY begin your reply with a short \texttt{\#\# Analysis} section (2-6 sentences diagnosing which previous
edit caused which regression or recovery -- state the cause before the fix; in round 1 you may use it to state your hypothesis instead).
The \texttt{\#\# Analysis} section is discarded automatically by the parser. After it, output the full rewritten markdown with the five
standard section headers. No other prose, no code fences, nothing after the last section.
\end{promptbox}

\subsection{Task-Specific Insertions}
\label{app:insertions}
\texttt{\{task\_description\}} supplies fixed task-specific guidance, quoted below. The MMLU

\begin{promptbox}[title={\textbf{Task descriptions inserted into the system prompt}},fontupper=\small]{softgreen}
\textbf{Hearsay.} a binary hearsay classification task under U.S. Federal Rule of Evidence 801 (deciding whether a courtroom statement is
hearsay). The output is Yes or No.\par
\textbf{MMLU.} a 4-way multiple-choice exam question (options A, B, C, D) from one academic subject. Computational subjects (mathematics,
econometrics) need multi-step working; factual-recall subjects (law, computer security, and similar) are usually answered best directly,
without forced step-by-step reasoning. The final answer is a single letter A, B, C, or D on an ``Answer:'' line.\par
\textbf{AIME.} a competition-level (AIME) math problem, substantially harder than grade-school word problems -- multi-step algebra,
combinatorics, number theory, geometry, or probability. The correct answer is always a specific integer between 0 and 999. The output
must end with a line containing the final numeric answer.\par
\textbf{IFBench.} an instruction-following task with the same mechanically verifiable constraint structure and the same
\texttt{FINAL RESPONSE:} marker convention as IFEval (see that description for the full explanation), but drawn from a broader set of constraint types (word/consonant/vowel counts,
keyword-frequency and forbidden-word rules, formatting requirements, and more). Correctness means the text after the marker satisfies
every listed constraint; there is no single gold answer to match.\par
\textbf{PUPA.} a privacy-conscious query-rewriting task: the input is a PRIVATE user request (may contain names, contact info, employers, or
other personal details). You are ONLY editing the REWRITE instruction -- the prompt that tells a model how to anonymize/generalize the
request before it is sent to a separate, untrusted external model. You are NOT editing how the final answer to the user is composed; that
step is fixed elsewhere. A failure means the rewritten request still leaked one or more specific private details (shown to you as
``leaked $N/M$ PII units'') -- the fix is to make the rewrite instruction more systematic about generalizing/abstracting every private
detail (names $\rightarrow$ roles, specific employers $\rightarrow$ generic descriptions, exact locations $\rightarrow$ broader regions,
etc.) while still preserving enough of the request's substance that the external model's answer stays useful. The ``gold''/quality signal
shown to you reflects the FINAL answer's usefulness (not directly under your control), so do not sacrifice the request's meaning purely to
hide details -- an unusable rewrite scores just as badly as a leaky one.
\end{promptbox}

\subsection{Worked Prompt Changes}
\label{app:evolution}
The excerpts below show the returned Task Details of two runs. Context and Constraints also changed in Hearsay;
System Role and Output Format were unchanged there, and IFBench's Output Format was pinned.

\paragraph{Hearsay, GPT-4.1 Mini.}
The seed's Task Details consisted of ``Decide whether the given statement is hearsay.'' The returned round-2 section
is reproduced below with formatting adjusted. Validation changed from 76.0\% to 96.0\%, while test accuracy changed
from 35/49 to 36/49: seven recoveries and six regressions. The explicit procedure raised validation sharply while
moving thirteen test outcomes for a one-item net gain.

\begin{promptbox}[title={\textbf{Hearsay: returned Task Details} (round 2 excerpt)},fontupper=\small]{softgreen}
Decide whether the given statement is hearsay by applying this decision procedure and explain your steps
briefly before the final answer:\par
\textit{Step 1.} Is there a ``statement''? Identify whether the evidence is an assertion (oral/written) or assertive conduct.
Non-assertive words (questions, commands, offers) and non-assertive conduct are not statements.\par
\textit{Step 2.} Was it made out of court? In-court testimony in this proceeding is not hearsay for this purpose.\par
\textit{Step 3.} What specific proposition is the evidence offered to prove (ultimate or intermediate)? Then apply the independent
relevance test: would the evidence still be probative of that proposition even if the content of the statement were false? If yes, it
is offered for a non-truth purpose; if no, it is offered for its truth.\par
\textit{Step 4.} If the evidence is offered solely for a non-truth purpose, answer No. Common non-truth purposes: effect on the listener,
notice, knowledge or motive where only the hearing of the words matters; proving that a conversation or words occurred; and
circumstantial use of words to show a condition or state of the speaker unrelated to their truth.\par
\textit{Step 5 (guardrail on embedded assertions).} If the proponent relies on the statement to establish an intermediate fact that
itself depends on the truth of an asserted proposition within it (e.g., ``I heard/know/saw X''), the statement is used for its
truth; treat as hearsay. Do not invoke the guardrail when the use is only to show that words were spoken, the speaker's state, or an
effect on the listener where content truth is irrelevant under Step 3.\par
\textit{Step 6.} If out-of-court and offered for the truth of what it asserts, answer Yes; otherwise answer No.
\end{promptbox}

\paragraph{IFBench, GPT-4.1 Mini.}
The seed's Task Details was ``Answer the user's request.'' Round 1 rewrote four sections, adding constraint extraction,
planning, and verification; the excerpt below shows its Task Details. Validation changed from 57.1\% to 71.4\%, and
test accuracy from 18/42 to 28/42 (twelve recoveries, two regressions). The \texttt{FINAL RESPONSE:} marker stayed fixed,
so only the post-marker answer was checked.

\begin{promptbox}[title={\textbf{IFBench: returned Task Details} (round 1 excerpt)},fontupper=\small]{softblue}
Your job is to: read the prompt and explicitly extract every constraint; plan content that satisfies all constraints
exactly; verify counts and formats on your draft before producing the final response. Prefer visible reasoning for these rule-application
tasks: write your working steps before the final answer line so you can check and fix issues. Only the content after the final marker is
scored.
\end{promptbox}

\subsection{Re-evaluation of an Unchanged Prompt}
\label{app:noise}
A GPT-4o-mini IFBench run that returned no edited prompt re-evaluated an unchanged prompt on the same 42 test items:
one outcome changed (no recoveries, one regression). The edited prompt of the main GPT-4o-mini IFBench run, which
started from a different seed prompt, changed five outcomes (two recoveries, three regressions).

\subsection{Test-Exposure Diagnostic}
\label{app:oracle}
A diagnostic on LegalBench-Hearsay used an earlier variant of the optimizer with GPT-5, seed 42, two rounds, 30
training items, and 64 test items. With the test items held out, accuracy changed from 44/64 to 47/64 (68.8\% to
73.4\%). Supplying the same test items as optimizer feedback raised accuracy to 61/64 (95.3\%), a gain more than five
times the held-out gain. This run is excluded from all other analyses.
